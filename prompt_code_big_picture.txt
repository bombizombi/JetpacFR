# The important distinction: graph versus timeline

A control-flow graph tells you:

> “Which code can lead to which other code?”

A trace tells you:

> “What actually happened, in what order, at what point in the game?”

You want both.

A graph loses time ordering once execution is aggregated. A timeline loses structure because it is just a long sequence. The most useful UI links them together.

For example, clicking a block in the graph should show:

- Every time it was executed.
- Its callers and successors.
- Which selected timeline regions caused it to appear.
- The surrounding execution sequence.
- Its first and last execution in the recording.

# Recommended “big picture” views

## 1. Memory/code atlas

Your global memory map idea is very good, but it should be an **overview and navigation tool**, not where comments are read in full.

Show logical memory as a compact heatmap:

- Execution count / cycles spent.
- Code discovered.
- Writes to code, useful for self-modifying code.
- Reads and writes.
- Region A/B comparison result.

At low zoom, a single pixel or rectangle might represent a page, such as 256 bytes. At closer zoom it becomes blocks, then instructions.

1. **Logical map**: `0000–FFFF` as seen by the CPU at a particular point.
2. **Physical map**: ROM/RAM banks as separate rows or cards.

Comments should appear as:

- A colored tick/flag.
- A short label when there is room.
- Full text in an inspector panel after selecting the region.

Do not try to render full comments inside a tiny memory atlas.

## 2. Dynamic call tree / flame graph

This may be the most useful answer to:

> “Which functions were involved in this gameplay action?”

Build a dynamic call tree from the recorded trace:

```text
GameFrame
  ReadInput
  UpdatePlayer
    CheckCollision
    UpdateSpritePosition
  DrawFrame
  InterruptHandler
```

Even if function detection is imperfect, this is extremely useful.

A flame graph is especially suitable:

- Width = time, cycles, or instruction count.
- Vertical nesting = call depth.
- Colour = selection membership or B-vs-A difference.
- Click to focus on a routine or call instance.

For the selected “move right” region, a routine that suddenly becomes wide or appears only in B is a strong candidate.

Allow users to:

- Rename a routine.
- Split a detected routine.
- Merge routines.
- Mark a jump as a tail call.
- Mark an address as an interrupt entry point or system routine.

## 3. Scoped control-flow graph

This is where your graph idea belongs.

Use **basic blocks**, not individual instructions, as the default node:

```text
$8A20-$8A2D
LD A,(keyState)
AND $01
JR Z,$8A2D
```

A block ends at a branch, call, return, jump target, interrupt entry, or similar control-flow boundary.

Each node can show:

- Address range.
- First instruction / a short mnemonic summary.
- Execution count.
- Cycles spent.
- A/B comparison badge.
- User routine name or comment icon.

Edges show:

- Fallthrough.
- Conditional taken/not-taken paths.
- Calls.
- Jumps.
- Returns, usually better represented through call containment than as giant cross-graph edges.
- Interrupt transitions.

Use edge thickness for execution count and edge colour for the selected comparison.

For example:

- Grey: common to A and B.
- Orange: disproportionately more active in B.
- Blue: disproportionately more active in A.
- Red: observed only in B.
- Dashed: statically possible but not observed in the recorded trace.

That last distinction matters. A conditional branch has two possible exits statically, but your movie may only have taken one of them. Showing observed and unobserved paths separately is very useful.

| Zoom level | What is visible |
|---|---|
| Far out | RAM banks, memory regions, major routine clusters |
| Medium | Routines and call relationships |
| Closer | Basic blocks and branch edges |
| Close | Normal instruction-level disassembly |

At far zoom, collapse things such as:

- Straight-line block chains.
- Loops.
- Detected routines.
- User-created groups.
- Interrupt handler code.

# Improve the A/B region comparison concept

What you already have is powerful. I would formalize it as a first-class feature called something like a **behaviour probe** or **experiment**.

Instead of attaching the same text comment to hundreds of instructions, create an object like:

```text
Hypothesis: Player moves right
Baseline: region A
Experiment: region B
Operation: B minus A
```

Then the application stores:

- The timeline selections.
- Their input state and frame range.
- The matching blocks/routines.
- Their execution counts in A and B.
- User comments and confidence.

Every view can then render the same hypothesis as a tag, colour, or badge.

Also compare rates, not only presence/absence. If region A is 10 seconds and B is 0.2 seconds, raw execution count is misleading. Compare something like:

- Executions per frame.
- Executions per emulated cycle.
- Executions per selected timeline duration.

You want to identify both:

- **B-only code**: likely branch-specific behaviour.
- **B-enriched code**: code that ran in both regions but much more often in B.

The latter is often important: a shared player update routine may run every frame, while only one tiny branch is right-specific.

A useful future view is a **behaviour matrix**:

| Routine/block | No input | Left | Right | Fire | Jump |
|---|---:|---:|---:|---:|---:|
| ReadInput | high | high | high | high | high |
| UpdatePlayer | medium | high | high | medium | high |
| MoveXPositive | 0 | 0 | high | 0 | 0 |
| MoveXNegative | 0 | high | 0 | 0 | 0 |

This becomes extremely powerful after you record several controlled playthroughs.

# About animated physics-style graphs

It can look beautiful, but I would not make a force-directed “nodes pull neighbours” layout the primary analysis mode.

For reverse engineering, stable layout matters more than beauty:

- Users learn where routines are.
- Screenshots remain comparable.
- Comments stay in meaningful places.
- Branch direction remains readable.
- Reopening a project does not rearrange everything.

Use a layered directed layout for CFGs: entry near the top or left, forward flow downward/rightward, loop edges bent backward.

You can still add pleasant interactive effects:

- Highlight the currently executing block during replay.
- Draw a fading trail over recently traversed edges.
- Animate one token along the active path while paused or scrubbing.
- Allow pinning nodes and perform a local re-layout around them.
- Provide a separate “exploration layout” mode if you want a physics view.

But avoid trying to animate every instruction during normal execution; at Z80 speed it will be visual noise.

# Important Z80-specific implementation details

Your graph node identity should not always be just `PC`.

For reliable trace analysis, identify executed code with something closer to:

```text
logical PC + paging/bank state + code generation/version
```

This matters because:

- On 128K machines, the same logical address can map to different physical RAM banks.
- Self-modifying code may cause the same address to execute different bytes at different times.
- Interrupts, especially the Spectrum interrupt path, should be shown as separate roots or lanes.
- Indirect jumps and returns may only be known dynamically.

Also, separate:

- **Static edges**: possible according to decoded instructions.
- **Observed edges**: actually taken in the movie.

For the first implementation, storing the trace as a sequence of **basic block IDs**, with timestamps/frame/cycle positions, is much more scalable than treating every instruction occurrence as a permanent graph node.

# Similar Applications & Prior Art

Your instincts are good — this is well-trodden territory in the reverse engineering world, and you can borrow heavily from it.

**RE tools worth studying:**
- **IDA Pro** — the gold standard for graph view of disassembly. Each basic block is a node, edges are control flow. Study how it groups instructions into *basic blocks* (straight-line code with one entry/exit) rather than one node per instruction — this is critical for you (see below).
- **Ghidra** (free, NSA) — has a function graph and a "function call graph." Open source, so you can look at how they lay things out.
- **Binary Ninja** — arguably the nicest graph rendering, with smooth zoom and semantic collapsing.
- **Cutter** (Rizin GUI) — free, and its graph view is web-tech adjacent.

**The key lesson from all of them:** don't make one node per instruction. Make one node per **basic block**. A basic block is a run of instructions with no branches in or out except at the ends. This collapses your graph by ~5-10x immediately and matches how humans read code. Individual instructions are shown *inside* the block node.

# Graph Layout Libraries (HTML/JS)

Your one-node-per-instruction "force-directed, pull neighbors around" idea is beautiful but **wrong for code flow**. Force-directed layouts produce organic blobs that hide the sequential/hierarchical nature of control flow. Code graphs want **hierarchical (layered) layouts** — top-to-bottom flow, like a flowchart. This is what IDA/Ghidra use.

**Recommended libraries:**

| Library | Notes |
|---|---|
| **Cytoscape.js** | Best all-round choice. Has the `dagre` and `elk` layout extensions for hierarchical flow. Handles compound/parent nodes (perfect for collapsing functions!). Great for large graphs. |
| **ELK.js** | The layout *engine* (Eclipse Layout Kernel). Best-in-class hierarchical layout with proper edge routing. Pair with a renderer. |
| **Dagre + D3** | Classic combo, dagre does layout, D3 renders. More manual work. |
| **Sigma.js** | Optimized for *very* large graphs (WebGL). Good if you hit performance walls. |
| **Reaflow / React Flow** | If you're in React. React Flow is pleasant for interactive node editing and comment-attaching. |

**My recommendation:** Cytoscape.js with the ELK layout extension. Its compound nodes give you the collapsible-function feature almost for free, it scales to thousands of nodes, and it supports the drag interactions you want.

**3. The graph view (structure/big picture of control flow)**

# Refining the Graph Idea

Here's how I'd make it genuinely useful rather than just pretty:

**Levels of zoom = levels of abstraction (semantic zooming):**
- **Zoomed all the way out:** Call graph. One node per *function*. Edges = "function A called function B." This is your true "big picture."
- **Medium zoom:** Control flow graph within a function. Nodes = basic blocks.
- **Zoomed in:** Individual instructions inside each block.

Bind zoom level to which representation shows. This is the single most powerful idea for "seeing the big picture."

**Auto-detect functions from the execution trace.** Since you have the actual execution movie, you can identify functions by watching `CALL`/`RET` pairs and stack behavior — even without static analysis. This sounds like an incredibly powerful tool for reverse engineering ZX Spectrum games. Here is a breakdown of applications that do similar things, HTML/JS libraries that would be perfect for this, and additional ideas to elevate your GUI.

### 1. Applications with Similar Features
Your ideas align closely with modern reverse engineering and dynamic analysis tools. You should look at these for inspiration:

*   **Ghidra (NSA):** Ghidra has an excellent "Control Flow Graph" (CFG) view. It groups instructions into "basic blocks" (blocks of code with no jumps in or out except at the start and end). You can zoom out to see the high-level flow, and zoom in to see individual instructions.
*   **Binary Ninja:** Known for having one of the best interactive CFG GUIs. It uses a "tree" layout that automatically routes edges nicely. It also collapses functions into single blocks when zoomed out.
*   **QIRA (Quite Interoperable Reverse Engineering):** This is a "timeless debugger." It records a whole execution and presents memory and instructions across a timeline, much like your execution mode.
*   **Revng / Triton:** These tools focus heavily on dynamic execution and building graphs from traces. 

### 2. HTML/JS Libraries for the Graph View
If your UI is HTML/JS-based (e.g., Electron, Tauri, or a web wrapper), you have excellent options for dynamic, physics-based graphing. 

*   **vis.js (vis-network):** This is probably the most out-of-the-box ready library for what you want. It has built-in physics simulations (force-directed layout). If you drag a node, its neighbors are pulled along. You can easily double-click a node to collapse/expand its children. It handles thousands of nodes reasonably well.
*   **React Flow (or Vue Flow / Svelte Flow):** If you are using a modern web framework, React Flow is the gold standard right now. While it doesn't have built-in "physics pulling" by default, you can integrate it with `d3-force`. Its main advantage is that you can build custom node components. You could make a node that displays the disassembly text, or a collapsed node that just says "Function: Move Right (45 instructions)" with a comments section attached.
*   **Cytoscape.js:** Very powerful, specifically designed for graph theory and network visualization. It has great layout algorithms (Dagre, Klay, Force) and handles large datasets better than vis.js. It supports compound nodes (nodes within nodes), which is perfect for your "collapse functions into a single bubble" idea.
*   **Dagre / Dagre-D3:** If you want a clean, hierarchical, top-to-bottom flowchart style (like Ghidra/Binary Ninja) rather than a floating physics blob, Dagre is the standard layout engine. You render it using D3.js.

### 3. Refining the Graph Idea: CFG vs Call Graph
A graph of *every single instruction* will become a chaotic spiderweb very quickly. Instead, consider two levels of graphs:

*   **Control Flow Graph (CFG) - Zoomed In:** Nodes are "Basic Blocks" (a sequence of instructions ending in a jump/branch). This keeps the graph clean.
*   **Call Graph - Zoomed Out:** Nodes are subroutines/functions. An edge means "Function A called Function B." This gives you the massive "big picture" of how the game handles the "Move Right" event. You can expand a function node to turn it into a CFG.

### 4. Additional GUI Improvements & Ideas

**A. Fix the Scrolling immediately with Virtualization**
If you are rendering a massive log and it lags or doesn't scroll, look into **virtualized lists**. Libraries like `react-window` or `vue-virtual-scroller` only render the DOM elements currently visible on screen. **B. The "Minimap" / Memory Heatmap**

*   Color-code the blocks based on execution frequency (e.g., cold blue for rarely executed, hot red for tight loops).
*   Overlay your timeline A/B regions on this map. You could visually see "During region B (Move Right), this specific chunk of memory lit up."

**C. Flame Graphs**
A Flame Graph is a visualization commonly used for CPU profiling, but it is *perfect* for execution traces. 
*   The X-axis is time (or instruction count).
*   The Y-axis is the call stack.
*   A block at the bottom is the main loop. Blocks on top of it are functions called by the main loop.
*   The width of the block represents how long the function took.
This instantly shows you the "big picture" of execution flow without needing a spiderweb graph. You could click a block in the flame graph to jump to the disassembly.

**D. Visual Diffing for your A/B Regions**

*   Left side: Code executed in Region A (No key pressed).
*   Right side: Code executed in Region B (Key pressed).

**E. Bookmark / "Breadcrumb" Side-bar**

**F. Register/Memory Peek-over**
In your execution mode disassembly, allow the user to hover over an instruction or a memory address (e.g., `LD A, (IX+5)`). A small tooltip should pop up showing the value of `A` or the memory at `IX+5` at that exact moment in the recorded movie timeline.

I would integrate **d3-force** to give it that physical, pull-your-neighbors feel. I would also strongly consider adding a **Flame Graph** as an alternative to the node-graph, as it often scales better to thousands of executed instructions.

Your graph-view idea is strong and aligns with proven reverse-engineering patterns. Instruction-as-node (or better: basic-block-as-node) graphs with predecessor/successor edges, branch fan-outs, zoom/collapse, and interactive layout are exactly how tools surface “big picture” control flow and behavior. Similar Applications / Tools
These do closely related things (CFG, execution-trace graphs, hierarchical collapse, interactive force/physics layouts, annotation):

rgat** (instruction-trace visualizer): Closest dynamic analogue. Builds graphs from instruction traces, supports force-directed (and other) layouts, heatmaps for hot paths, animation/replay of the trace, zooming into blocks/instructions, and live or post-mortem views. Explicitly aimed at linking observed behavior back to code. GPU-accelerated layout in later versions. Great reference for “execution movie → graph.”
IDA Pro, Ghidra, Binary Ninja**: Standard interactive CFG views (basic blocks as nodes, colored true/false/unconditional edges). Zoom, pan, overview minimaps, node selection, comments/labels on blocks/functions. Ghidra and Binary Ninja support good hierarchical / call-graph views and proximity browsing. Binary Ninja is especially polished for interactive navigation and function graphs. These are static (or debugger-augmented) rather than pure-trace, but the UX patterns transfer directly.
CFGExplorer** (and related academic tools): Interactive CFG visualization that works especially well with instruction traces; supports linking between the linear trace and the node-link view, loop/function collapsing, and custom highlighting.
Spectrum Analyser** (Colourclash / 8BitAnalysers project): The most relevant ZX Spectrum-specific tool. Built-in emulator + interactive disassembler, automatic code/data detection from execution, frame-trace / timeline scrubbing (last N frames with instruction traces and screen writes), memory diffs, annotation (labels, comments, functions), graphics viewer, breakpoints, SkoolKit import/export, etc. It already solves many of the “play a segment → inspect what ran” problems you have; studying its timeline + disassembly interaction is worthwhile even if you keep your own engine.
Others worth glancing at: BinNavi (graph-centric RE with custom graphs and traces), angr-management / cfg-explorer (CFG recovery + SVG/web views), various call-graph / dependency visualizers, and academic trace tools that turn execution into force-directed or hierarchical graphs.

Your differential-region commenting (“everything in B but not A → mark as ‘player move right’”) is a nice unique twist that most of the above lack; layering that onto a graph would be distinctive.

HTML / JS Libraries for the Graph View
For an interactive, zoomable, collapsible, force/physics-based display (nodes that can be dragged and pull neighbors, collapse groups into super-nodes, attach names/comments), these are the practical choices:

| Library          | Strengths for your use-case                          | Trade-offs                          | Recommendation |
|------------------|-----------------------------------------------------|-------------------------------------|---------------|
| Cytoscape.js | Excellent compound/hierarchical nodes (perfect for collapsing functions or basic-block groups), many layouts (force-directed/fcose, hierarchical, etc.), rich styling, events, analysis algorithms, good performance up to a few thousand nodes | Slightly more setup than pure physics libs | Strong first choice for CFG + collapse |
| vis-network (vis.js) | Built-in physics simulation, easy drag/pull-neighbors, clustering, very quick to get interactive | Clustering is coarser; less graph-theory power | Great if you want the “beautiful interactive physics” feel fast |
| force-graph / react-force-graph (or ngraph + custom) | Highly performant force-directed, particles on edges for flow, good for animation of execution | Less built-in hierarchy | Excellent for dynamic “replay the movie on the graph” |
| Sigma.js     | WebGL, scales to very large graphs                  | Less out-of-the-box hierarchy/physics polish | Use if traces produce huge node counts |
| D3-force + custom SVG/Canvas or JointJS / dagre + renderer | Maximum control | More code to write | Only if you need something the others can’t do |

Practical suggestion: Start with Cytoscape.js (or vis-network if the pure physics “nodes pull neighbors” feel is the highest priority). Both support:
Zoom/pan, node drag with physics,
Compound nodes / grouping for collapsing functions or “logical regions,”
Custom labels, tooltips, and data attributes for your comments/names,
Edge styling for branches (true/false colors, thickness by execution count),
Filtering/highlighting by your timeline regions.

You can feed it either a static CFG recovered from the executed instructions or a dynamic execution graph (nodes = unique instructions or basic blocks seen in the trace; edges = observed succession, with multiplicity or animation for the “movie”).

For pure hierarchical CFG layout (less “force soup,” more readable control-flow), pair with dagre, elkjs, or Cytoscape’s hierarchical layouts. Many people render a dagre/elk layout first, then optionally switch to force for exploration.

Concrete Graph Design Recommendations
Prefer basic blocks (or short straight-line sequences) as primary nodes rather than individual instructions; collapse further into functions or user-named regions. Individual instructions become too dense quickly.
Edges: sequential fall-through + explicit branch targets. Color or animate the edges that were actually taken in the selected timeline region(s). Thickness or glow by execution frequency.
Collapse rules: auto-detect functions (via call/ret or your own heuristics), or let the user lasso/group nodes and name them. Super-nodes show aggregated comments and a summary of the differential markings from the timeline.
Dual linking: click a node → jump/highlight in the linear disassembly or the execution-log view; select a timeline region → highlight the corresponding subgraph and fade everything else.
Animation: “play” the recorded movie by walking a token/particle along edges or temporarily highlighting the active path. This makes the big-picture execution order obvious.
Overview + detail: keep a minimap or a coarser memory-map strip; the detailed graph is only the currently focused region or the differential set.
Persistence: store the collapsed groups, names, and comments so they survive across sessions (and can be exported alongside SkoolKit-style annotations if you want interoperability).
