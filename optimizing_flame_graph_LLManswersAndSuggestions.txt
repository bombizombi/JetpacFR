## Your assumption is wrong — but in a fixable way

The 64 KB limit bounds the number of **distinct functions** (realistically a few hundred), not the number of **rectangles**. A flame graph rectangle is one *invocation*, and invocations scale with time, not with memory.

Quick arithmetic for a Spectrum-class machine (3.5 MHz, ~70,000 T-states/frame, 50 fps):

- `CALL` + `RET` cost 27 T-states minimum, so a frame can contain up to ~2,500 calls.
- A realistic game does maybe 200–2,000 calls per frame (sprite routines in loops, per-row/per-column helpers, keyboard scans, sound driver, etc.).
- 500 calls/frame × 50 fps = 25,000 rectangles **per second** of emulated time. A 2‑minute trace is ~3 million rectangles. A 10‑minute trace is 15 million.

So "60,000 rectangles, no problem" is off by two or three orders of magnitude, and yes, WPF will choke on millions of anything — especially if they are `Rectangle` UIElements.

The good news: **the number of rectangles you ever need to draw is bounded by pixels, not by data.** At any zoom level, each row (stack depth) can contain at most `viewport_width_in_pixels` visible rectangles. With a 2,000-px-wide window and a stack depth of 20, that's 40,000 rects worst case, and usually far fewer. Anything narrower than a pixel gets merged. Once you design around that, the trace length becomes irrelevant to paint speed.

## Architecture

### 1. Separate the call-event log from the frame snapshots

Don't derive the flame graph by replaying the trace on startup. Record a compact, append-only **call event log** while executing:

```
struct CallEvent {
    ulong tstate;      // absolute T-state since trace start (64-bit)
    ushort address;    // callee entry (for enter) / caller (for exit)
    byte   depth;
    byte   kind;       // Call, Rst, Ret, IntEnter, IntExit, TailJump, StackFixup
}
```

12–16 bytes per event, so a 10-minute trace is ~200–400 MB uncompressed, much less compressed (deltas on `tstate` and a small dictionary of addresses compress extremely well). Save it next to the trace file. Memory-map it on load so startup cost is zero.

From this, build **closed intervals per depth row**: `(start, end, functionId)`, sorted by start. That's your primary render model. Keep it as flat arrays (`ulong[] start`, `ulong[] end`, `ushort[] func`) per depth — struct-of-arrays, no objects, binary-searchable.

Because you already have deterministic per-frame snapshots, if an old trace lacks the event log you can **rebuild it in parallel**: hand each core a range of frames, replay from the snapshot, emit events. This is embarrassingly parallel and is the single biggest win for "fast on first start" with legacy traces.

### 2. Getting the call stack right on a Z80

The Z80 has no frame pointer and programs cheat constantly. Track depth from **SP**, not from opcode pairing alone:

- `CALL cc / RST / interrupt entry` → push a frame tagged with the return address and the SP value.
- `RET cc / RETI / RETN` → pop until you find the frame whose SP matches the current SP after the pop. This automatically handles `POP`-and-`RET` tricks, `JP (HL)` dispatch tables, `PUSH addr; RET` jumps, and routines that discard their return address.
- If SP jumps wildly (`LD SP,xxxx`), emit a `StackFixup` event and reset the stack; render that as a visible marker rather than corrupting everything afterwards.
- Treat tail jumps (`JP` to a known function entry) as optional "TailJump" rects; a lot of Z80 code is `JP` chains and users will want to see them, but make it toggleable.

Function identity = entry address. Give each distinct entry a small integer ID and a colour from a fixed palette (hash of address, or user-assignable). Symbol names from your disassembler labels map onto the ID table.

### 3. Level-of-detail (mipmapped) intervals

This is the part that makes zoom and scroll constant-time regardless of trace length.

For each depth row, precompute a pyramid of downsampled rows. Level *k* buckets time into 2^k T-state cells; each cell stores:

- the dominant `functionId` (by covered time) and its coverage fraction, or
- a `Mixed` marker if no single function dominates (render as grey/hatched).

Optionally also store a per-cell histogram of the top 2–3 functions if you want nicer blending.

When rendering, pick the level where one cell ≈ one pixel. The paint loop becomes: for each depth row, for each pixel column, look up one cell. That's `width × maxDepth` lookups — a few tens of thousands — regardless of whether the trace is 10 seconds or 10 hours.

The pyramid is roughly 2× the size of the base data (geometric series), can be built lazily per level, built in the background on load, and saved to disk with the trace so subsequent starts are instant. Build coarse levels first so you can show *something* in the first 100 ms and refine.

When zoomed in far enough that cells are wider than pixels, fall back to the raw interval arrays: binary search for the first interval whose end ≥ viewport start, iterate until start > viewport end. That's O(log n + visible).

Frame boundaries are a natural coarse level too: a "frames" row with one cell per frame is what you'd show fully zoomed out, and it doubles as the navigation strip / minimap.

### 4. Rendering in WPF: don't use the retained-mode tree

Ranked from "fine" to "fastest":

1. **`DrawingVisual` + `DrawingContext.DrawRectangle`** with frozen brushes. OK up to ~10–20k rects per repaint if you batch by colour (one `StreamGeometry` per colour, one `DrawGeometry` call each). Works, but 60 fps scrolling is marginal.
2. **`WriteableBitmap`**, filled directly with the pixel loop from step 3 on a background thread, then `AddDirtyRect`. This is the natural fit: a flame graph at LOD is literally "for each column, for each row, set a colour". You can paint a 4K image in a couple of milliseconds. Cache the bitmap; on horizontal scroll, blit the overlapping part and only compute the newly exposed strip; on zoom, recompute (still ~ms).
3. **SkiaSharp (`SKElement`) or a Direct2D/D3D host (Vortice / SharpDX)** if you want anti-aliasing, GPU text, and 144 Hz smoothness. Probably unnecessary once 2 is done right, but it's the escape hatch.

Whatever you pick:

- Draw **only the viewport**. Never build geometry for the whole trace.
- Render **text only for rects ≥ ~40 px**, using cached `GlyphRun`/`FormattedText` per function ID (WPF text layout is slow; cache the layout, not just the string). Clip text to the rect.
- **Coalesce input**: mouse-wheel and drag events fire far faster than you need to repaint. Set a "dirty viewport" and repaint once per `CompositionTarget.Rendering` tick (or a 16 ms `DispatcherTimer`), taking the latest viewport only.
- **Render off the UI thread** into a back buffer; swap on completion. If a render is in flight when the viewport changes again, let it finish and then render once more with the newest viewport — never queue up.
- Freeze all brushes/pens; index them by function ID in an array. No allocations in the paint path.
- Hit testing for hover/click: binary search the raw interval array for the row under the mouse; don't rely on WPF hit-testing of visuals.

### 5. Tie it to the debugger

- Time axis is **absolute T-states**, 64-bit. Frame number, scanline, and instruction index are all derived views; keep a `frameStartTstate[]` array to binary-search between them.
- Clicking a rect → `(frame, tstateWithinFrame)` → restore snapshot for that frame, replay forward to the T-state. Your existing "step backward" mechanism is exactly this operation, so the flame graph becomes a random-access time slider for free.
- Show the current PC/time as a cursor line on the graph and keep the flame graph row for the current stack highlighted — cheap, since you have depth and function ID in the same arrays.

### 6. Startup path summary

1. Memory-map trace + call-event log + LOD pyramid (if present).
2. Restore last frame snapshot → show screen. (You already do this.)
3. Render flame graph from coarsest LOD level immediately (frame row).
4. Background: build/verify finer LOD levels, or rebuild the event log from snapshots in parallel if it's missing; invalidate the viewport as each level lands.

Done this way, paint time depends on window size and stack depth only, and a multi-hour trace scrolls as smoothly as a two-second one.

This is a fascinating project. Building a deterministic time-travel debugger for the Z80 with full state snapshots is an impressive engineering feat.

However, to answer your core question directly: **Yes, you are wrong in your assumption regarding the 64KB memory limit and the number of rectangles.**

Here is the breakdown of why your performance is suffering, followed by architectural solutions to make it fly.

### 1. The Assumption Check: Memory vs. Time
You assumed: *64KB Memory $\rightarrow$ Max ~60,000 Rectangles.*

**Why this is incorrect:**
A flame graph (or execution trace visualization) represents **time** and **call stack depth**, not memory addresses.
*   **Memory Limit:** The Z80 has 64KB of addressable space. This limits the number of *unique* function entry points (code addresses).
*   **Execution Volume:** A Z80 runs at roughly 3.5 MHz. A single video frame (at 50Hz) is 20ms, which is roughly **70,000 T-states**.
*   **Function Calls:** A simple function call might take 50 T-states. In a single frame, a tight loop could call a function **1,000+ times**.
*   **The Trace:** If your trace covers 10 seconds of execution, that is 500 frames. If each frame has 1,000 function calls, you are looking at **500,000 rectangles**, not 60,000.

Even if you limit it to 60,000 rectangles, **WPF cannot handle 60,000 interactive UI elements efficiently.**

### 2. The WPF Bottleneck: The Visual Tree
In WPF, every `Rectangle` you add to a panel is a `UIElement`.
*   **Overhead:** Each element has a logical tree node, a visual tree node, layout caching, property system overhead, and event routing.
*   **Cost:** Creating and maintaining 10,000 `UIElement`s is often the tipping point where WPF UI becomes sluggish. At 60,000, scrolling and zooming will inevitably lag because the layout system and renderer are choked by the sheer number of objects in the tree.

### 3. Architectural Solutions for Speed

To make this paint fast (60fps) even on first load, you need to move away from "One Rectangle = One UIElement."

#### A. Custom Rendering (The Biggest Win)
Do not create `Rectangle` controls. Instead, create a **single custom control** that draws all the rectangles itself using the low-level rendering API.

**Option 1: `OnRender` with `DrawingContext`**
Override the `OnRender` method of a custom `FrameworkElement`. Use the `DrawingContext` to draw rectangles directly.
*   **Pros:** No visual tree overhead for individual bars.
*   **Cons:** Still retains some WPF layout overhead.

**Option 2: `DrawingVisual`**
Host a `DrawingVisual` inside a `FrameworkElement`. This gives you direct access to the rendering thread's command stream without the full `UIElement` baggage.

**Option 3: `WriteableBitmap` (High Performance)**
Render the graph to a `WriteableBitmap` on a background thread and display that bitmap in an `Image` control.
*   **Pros:** Extremely fast. The UI thread just swaps a texture.
*   **Cons:** You must handle DPI scaling and zooming logic manually (redraw bitmap on zoom).

**Option 4: SkiaSharp (Recommended)**
Use **SkiaSharp** (a cross-platform 2D graphics engine) hosted in WPF (`SKElement`).
*   Skia is hardware accelerated, extremely fast, and designed for drawing thousands of primitives.
*   It handles zooming/panning transforms much better than WPF's layout system.

#### B. Level of Detail (LOD) / Aggregation
You cannot draw every single function call when the user is zoomed out to view a 10-second trace.
*   **Zoomed Out:** If 1 pixel on the screen represents 100 T-states, do not draw 10 rectangles. **Aggregate them.** Draw one rectangle representing the "dominant" function in that time slice, or a heat-map color indicating intensity.
*   **Zoomed In:** As the user zooms in, swap to a higher-resolution data structure that allows drawing individual call instances.
*   **Implementation:** Pre-calculate mipmaps or hierarchical data structures for your trace data.

#### C. Viewport Virtualization
Never iterate over the *entire* trace to draw the frame.
1.  Calculate the visible time range based on scroll/zoom offset.
2.  Query your data structure for only the function calls that intersect that visible range.
3.  Draw only those.
4.  **Data Structure:** You need an index. A simple `List<TraceEntry>` requires O(N) search. Use a **spatial index** or a **time-indexed array** (e.g., an array where index = T-state / 100) to jump to the visible start point in O(1).

#### D. Data Pre-processing
Do not parse the trace and build the graph geometry on the UI thread.
*   **Background Worker:** When loading a trace, parse the Z80 execution log on a background thread.
*   **Flattened Geometry:** Convert the trace into a flat array of "Draw Commands" (X, Y, Width, Height, Color).
*   **Freezing:** If you stick with WPF brushes/pens, ensure you call `.Freeze()` on them to make them thread-safe and faster.

### 4. Proposed Architecture Diagram

Here is how you should restructure the rendering pipeline:

```text
[ Z80 Trace Data ] (Raw T-states, PC, Stack)
       |
       v
[ Data Processor ] (Background Thread)
       | -> Builds "Time-Indexed Buckets"
       | -> Aggregates calls for LOD levels
       v
[ View Model ]
       | -> Calculates Visible Range (Scroll/Zoom)
       | -> Requests Visible Data from Processor
       v
[ Render Engine ] (SKiaSharp or DrawingVisual)
       | -> Iterates ONLY visible items
       | -> Draws primitives directly to surface
       v
[ Screen ]
```

### 5. Specific Implementation Advice (WPF + SkiaSharp)

If I were building this today, I would use **SkiaSharp.Views.WPF**.

1.  **Install NuGet:** `SkiaSharp.Views.WPF`
2.  **The Control:**
    ```xml
    <skia:SKElement x:Name="FlameGraph" PaintSurface="OnPaintSurface" />
    ```
3.  **The Code:**
    ```csharp
    private void OnPaintSurface(object sender, SKPaintSurfaceEventArgs e)
    {
        var canvas = e.Surface.Canvas;
        canvas.Clear(SKColors.White);

        // 1. Calculate visible range based on _scrollOffset and _zoomLevel
        var visibleStartTState = _scrollOffset * _zoomLevel;
        var visibleEndTState = visibleStartTState + (e.Info.Width * _zoomLevel);

        // 2. Query optimized data structure (O(1) or O(log N))
        // Do NOT iterate the whole list
        var visibleCalls = _traceIndex.GetCallsInRange(visibleStartTState, visibleEndTState);

            float x = (call.StartTState - visibleStartTState) * _pixelsPerTState;
            float y = call.StackDepth * _rowHeight;

            // Color code by function address or type
            paint.Color = GetColorForFunction(call.Address);

            canvas.DrawRect(x, y, call.Duration * _pixelsPerTState, _rowHeight, paint);
        }
    }
    ```

### 6. Summary Checklist for Performance

1.  **Correct the Math:** Accept that you may have hundreds of thousands of call instances, not limited by RAM size.
2.  **Kill the Visual Tree:** Stop adding `Rectangle` children to a `Canvas` or `Grid`. Use `OnRender`, `DrawingVisual`, or SkiaSharp.
3.  **Virtualize:** Only process and draw data currently visible in the viewport.
4.  **Index:** Create a time-based index for your trace data so you don't have to scan the list to find where to start drawing.
5.  **LOD:** Implement aggregation so that zooming out reduces the number of draw calls, not just the size of the rectangles.
6.  **Freeze Resources:** If using WPF brushes, freeze them.
7.  **Hit Testing:** If you need click-to-select a function, do not rely on WPF hit testing on 60k elements. Calculate the hit mathematically based on mouse coordinates vs. visible data range.

By switching to a retained-mode graphics engine like Skia or even just WPF's `DrawingContext` with virtualization, you should be able to render hundreds of thousands of rectangles at 60fps easily.

No — **the 64 KB limit does not imply a maximum of ~60,000 rectangles in your flame graph**. That's the important misconception.

The good news is that **60,000 rectangles is absolutely not a scary number for WPF** if you're rendering them intelligently. If your flame graph is sluggish while panning/zooming, I would strongly suspect the problem is **how the rectangles are represented, laid out, invalidated, and rendered**, rather than the raw number of rectangles.

Also, your architecture has a particularly nice property: the trace is essentially a **time-indexed immutable dataset**. You can exploit that very aggressively.

### 1. 64 KB doesn't bound the number of trace rectangles

The Z80 can only address 64 KB of memory at a time, but your trace contains **history**, not just machine state.

For example, suppose a function occupies address `$8000`. It can appear:

```text
frame 1:   $8000 → $8010
frame 2:   $8000 → $8010
frame 3:   $8000 → $8010
...
frame 500000: $8000 → $8010
```

That's potentially **hundreds of thousands or millions of function invocations**, despite there being only 65,536 possible addresses.

And there's another distinction:

* **unique functions / code locations** → bounded by address space
* **function invocations** → not bounded by address space
* **stack frames** → not bounded by address space over time
* **rectangles representing invocations** → potentially enormous

If your flame graph has one rectangle per invocation, the trace length is the relevant bound, not 64 KB.

---

# 2. But 60,000 rectangles should still be easy

Absolutely.

A modern desktop GPU can deal with vastly more geometry than that. Even CPU-side rendering of 60k simple rectangles can be perfectly responsive.

The problem is that WPF has a very important trap:

### Don't make 60,000 WPF elements.

This:

```text
Canvas
 ├── Rectangle
 ├── Rectangle
 ├── Rectangle
 ├── Rectangle
 ...
 └── Rectangle × 60000
```

is quite different from:

```text
CustomControl
    ↓
OnRender()
    ↓
draw 60,000 rectangles
```

The first creates tens of thousands of objects participating in WPF's:

* dependency-property system
* layout
* measure
* arrange
* visual tree
* hit testing
* invalidation
* rendering

That can get expensive very quickly.

The second can be extremely fast.

**For a flame graph, I would use one custom WPF control and render the entire graph yourself.**

Something along the lines of:

```csharp
protected override void OnRender(DrawingContext dc)
{
    // determine visible time range

    // determine visible stack/function rows

    // draw visible rectangles
}
```

No `Rectangle` controls. No giant visual tree.

---

# 3. The biggest optimization: don't render what isn't visible

This is probably the most important architectural principle for your application.

Suppose your trace contains:

```text
10,000,000 function calls
```

but the current viewport can only display:

```text
2,500 rectangles
```

You shouldn't even *consider* the other 9,997,500 rectangles during painting.

Your renderer should operate approximately like:

```text
trace
  ↓
visible time interval
  ↓
visible stack/depth interval
  ↓
visible calls
  ↓
paint
```

not:

```text
trace
  ↓
iterate 10 million calls
  ↓
check whether each is visible
  ↓
paint 2,500 of them
```

That distinction becomes enormous when zooming and scrolling.

---

# 4. Build a spatial index

Your trace is especially suitable for this.

Give every flame rectangle something like:

```text
StartTime
EndTime
Depth
FunctionId
```

Then organize the data by time.

For example:

```text
Trace
 ├── time chunk 0
 ├── time chunk 1
 ├── time chunk 2
 ├── ...
 └── time chunk N
```

Perhaps each chunk represents 1,000 / 10,000 / 100,000 frames.

Then when the user zooms into:

```text
frame 2,340,000 → 2,345,000
```

you immediately know which chunks intersect that region.

You don't scan the entire trace.

A simple binary search can also get you to the first relevant event extremely quickly if the events are sorted by time.

---

# 5. Go one step further: build multiple resolutions

This is where I think your flame graph could become **really** fast.

A flame graph is fundamentally a visualization of time.

At extreme zoom-out, individual function calls aren't even visually distinguishable.

Imagine:

```text
10,000,000 calls
       ↓
screen has 2,000 horizontal pixels
```

There is absolutely no reason to render 10 million rectangles.

Instead, construct a hierarchy of representations:

```text
Level 0: individual calls

Level 1: aggregate ~100 calls

Level 2: aggregate ~10,000 calls

Level 3: aggregate ~1,000,000 calls
```

Then:

```text
ZOOMED OUT
    ↓
aggregate representation

ZOOM IN
    ↓
more detailed representation

ZOOM IN
    ↓
individual calls
```

This is essentially a **level-of-detail (LOD)** system.

It can make zooming from millions of events to individual calls feel instantaneous.

---

# 6. You can exploit the 64 KB address space very effectively

There *is* a very useful consequence of the Z80's small address space — just not the one you proposed.

You can represent functions extremely compactly.

For example:

```csharp
ushort FunctionAddress;
```

instead of:

```csharp
long FunctionAddress;
```

And create a function table:

```text
FunctionId
    ↓
FunctionInfo
    ├── address
    ├── name
    ├── symbol
    ├── color
    └── metadata
```

Then every trace event can contain something like:

```text
StartFrame
EndFrame
FunctionId
Depth
```

rather than repeatedly storing strings or large objects.

For millions of events, this makes a **huge** difference to memory locality and cache behavior.

---

# 7. Don't put strings/objects in the trace

I'd strongly recommend a data-oriented representation.

Something like:

```csharp
struct TraceEvent
{
    public int StartFrame;
    public int EndFrame;
    public ushort FunctionId;
    public ushort Depth;
}
```

Or, even better, separate arrays:

```text
startFrames[]
endFrames[]
functionIds[]
depths[]
```

This is essentially a **struct-of-arrays (SoA)** layout.

It can be considerably faster for rendering because your renderer might only need:

```text
startFrame
endFrame
functionId
depth
```

and can stream through contiguous memory.

For a debugging application dealing with millions of events, this kind of thing can matter much more than people initially expect.

---

# 8. Cache the expensive parts of rendering

Your function rectangles presumably have properties like:

```text
function → name
function → color
function → formatted label
```

Don't recompute these every frame.

Precompute:

```text
FunctionId 0 → Drawing data
FunctionId 1 → Drawing data
FunctionId 2 → Drawing data
...
```

And potentially cache:

```text
FunctionId + zoom level
```

for text/layout decisions.

For example, don't repeatedly ask:

> "Is the text 'RenderSprite' going to fit inside this rectangle?"

for thousands of rectangles during every mouse movement.

Instead, have a cheap rule:

```text
if width < 40px:
    don't draw text

if width >= 40px:
    draw cached text
```

# 9. Separate the data model from the renderer

I'd structure the system roughly like this:

```text
                 ┌─────────────────────┐
                 │     Trace Store     │
                 │                     │
                 │ frames              │
                 │ CPU states          │
                 │ memory snapshots    │
                 │ input               │
                 │ calls               │
                 └──────────┬──────────┘
                            │
                            ▼
                 ┌─────────────────────┐
                 │   Trace Index       │
                 │                     │
                 │ time → events       │
                 │ frame → state       │
                 │ function → calls    │
                 └──────────┬──────────┘
                            │
                            ▼
                 ┌─────────────────────┐
                 │ Flame Graph Model   │
                 │                     │
                 │ viewport            │
                 │ zoom                │
                 │ LOD                 │
                 │ visible events      │
                 └──────────┬──────────┘
                            │
                            ▼
                 ┌─────────────────────┐
                 │ WPF Custom Control  │
                 │                     │
                 │ OnRender()          │
                 └─────────────────────┘
```

The renderer shouldn't know anything about emulation, snapshots, Z80 state, etc.

It should receive:

> "Here are the 1,800 things visible in the current viewport."

and paint them.

# 10. Your frame snapshots are also an opportunity

Your debugging architecture sounds very good.

You effectively have:

```text
Snapshot[N]
    +
inputs[N+1 ... M]
    ↓
replay
    ↓
Snapshot[M]
```

That means you can choose snapshot granularity independently of the visual trace.

For example:

```text
Frame 0
   |
Frame 100
   |
Frame 200
   |
Frame 300
```

Then jumping to frame 287 means:

```text
restore frame 200
execute 87 frames
```

But you don't necessarily want your **debugger storage format** and your **visualization format** to be the same thing.

I'd make those two systems independent.

---

# 11. Consider memory-mapped trace storage

If traces can become large, another architectural improvement is to avoid loading the whole trace into ordinary managed objects.

A file could be something like:

```text
TRACE FILE
│
├── header
├── function table
├── frame index
├── CPU snapshots
├── memory snapshots
├── input events
├── execution events
└── flamegraph index
```

Then use memory mapping / random access for the large sections.

This gives you a very nice property:

> Opening a 2 GB trace doesn't necessarily mean allocating and constructing a 2 GB object graph.

The OS can page in the portions you're actually using.

This is particularly attractive for a debugger.

---

# 12. Don't redraw the entire screen during scrolling if you don't need to

This is another area I'd investigate.

If the user scrolls horizontally by 5 pixels, you don't necessarily want your entire application architecture to interpret that as:

```text
destroy visualization
recalculate everything
layout everything
render everything
```

Instead, have a lightweight viewport:

```text
Viewport:
    X = 2,340,000
    Width = 2,000 frames
    Y = 5
    Height = 600
```

and make rendering a pure function of:

```text
Trace + Viewport → Pixels
```

That makes pan/zoom operations incredibly cheap.

# 13. WPF-specific recommendation

For this particular application I'd seriously consider:

### One custom `FrameworkElement`

Something like:

```text
FlameGraphControl
```

with:

```csharp
OnRender(DrawingContext dc)
```

and perhaps:

```csharp
OnMouseMove(...)
OnMouseWheel(...)
OnMouseDown(...)
```

The control maintains:

```csharp
double Zoom;
long FirstFrame;
int TopDepth;
```

and renders only the visible region.

I would **not** use:

* one `Rectangle` per call
* one `Border` per call
* one `TextBlock` per call
* nested WPF panels representing the call hierarchy

unless the number of visible elements is tiny.

# 14. An even faster option: render to a bitmap

If you're aiming for an exceptionally smooth visualization, you can go one level lower.

Instead of asking WPF to retain thousands of drawing primitives, your flame graph renderer can produce a bitmap for the current viewport:

```text
Trace
   ↓
FlameGraphRenderer
   ↓
WriteableBitmap
   ↓
WPF Image
```

Then panning/zooming becomes:

```text
calculate visible region
       ↓
render pixels
       ↓
display bitmap
```

For a diagnostic tool, this can be extremely effective.

You can also render off the UI thread and swap the resulting bitmap onto the UI thread.

The UI then remains responsive while a more expensive visualization is being prepared.

# 15. One thing I would measure before changing anything

Don't guess.

Put a profiler around:

```text
Trace loading
Trace indexing
Flame graph model construction
Viewport calculation
Visible-event selection
WPF layout
WPF rendering
Text rendering
GC
```

I would particularly look for:

### A. Number of WPF visual elements

If it's tens of thousands → **very likely a major culprit.**

### B. Allocations during mouse wheel / scrolling

If every scroll produces thousands/millions of allocations → fix that first.

### C. CPU time in `OnRender`

If `OnRender` is cheap but the UI is slow → the problem is probably elsewhere.

### D. Number of events examined per frame

This is perhaps the most interesting metric.

You want something like:

```text
10,000,000 events in trace
       ↓
1,700 events examined
       ↓
1,200 rendered
```

not:

```text
10,000,000 events
       ↓
10,000,000 examined
       ↓
1,200 rendered
```

```text
                       │

             │ Viewport + LOD     │
             │                    │
             │ 10M calls          │
             │       ↓            │
             │ 2K visible items   │
             └─────────┬──────────┘
                       │

              │ Custom WPF       │
              │ OnRender         │
              │                  │

              └──────────────────┘
```

And I'd make **opening the application not require constructing the flame graph at all**.

Load:

```text
trace header
function table
frame index
```

immediately.

Then display the final frame/screen immediately.

Build heavier indexes lazily in the background:

```text
UI thread
  └── show application

background
  ├── build flame index
  ├── build aggregates
  ├── prepare LOD levels
  └── warm caches
```

That would give you a very fast "open trace → see final screen" experience while the analytical machinery is being prepared behind the scenes.

### The key mental model

Don't think:

> **"I only have 64 KB, therefore I only have 64K rectangles."**

Think:

> **"I have a tiny address space but an arbitrarily long temporal history."**

And then:

> **"Regardless of how large the history is, the renderer should only touch the tiny fraction that can affect the current viewport."**

If you design around that principle, **millions of recorded calls shouldn't necessarily make scrolling feel any slower than thousands**.

=-================= glm 5.2

















You have built a highly sophisticated deterministic debugger. Time-traveling debugging and flame graph generation for a Z80 machine are fantastic features, but they introduce unique performance challenges. 

To answer your first question directly: **Your assumption about 60,000 rectangles is slightly flawed in two ways, but your conclusion that it should be fast is correct—with the right architecture.**

Here is why it's sluggish, followed by architectural ideas to make it blazingly fast.

### Part 1: Why your assumption is flawed (and why WPF is struggling)

1. **The 64KB limit limits *code*, not *execution*.** 64KB means there are only so many *unique* functions. However, a function can be called thousands of times per frame. If your flame graph draws a rectangle for *every function invocation* (which is how standard flame graphs work), a single frame could have hundreds of thousands of rectangles. Over an entire trace, you could be looking at millions of rectangles.
2. **WPF's Retained Mode Overhead:** WPF is a retained-mode UI framework. If you use standard `<Rectangle/>` elements or `ItemsControl`, WPF creates a UI element for each rectangle, allocates memory, calculates layout, builds a visual tree, and maintains hit-testing for every single one. Drawing 60,000 WPF `Rectangle` objects will absolutely cripple the UI thread. 

However, 60,000 (or even 600,000) rectangles are trivial for a modern GPU to draw **if you use immediate-mode rendering or hardware-accelerated bitmaps**.

### Part 2: Architectural Ideas for the Flame Graph UI

To make the flame graph paint instantly, scroll smoothly, and zoom without stuttering, you must abandon standard WPF UI elements for this specific component. 

**1. Use a Single `WriteableBitmap` or `SkiaSharp` Canvas**
Instead of adding `Rectangle` objects to a `Canvas`, treat the flame graph as a single image. 
* Use `SkiaSharp` (via `SKElement` in WPF). Skia is a 2D graphics engine that handles tens of thousands of rectangles effortlessly.
* When the user scrolls or zooms, you calculate which rectangles are visible in the viewport, and draw *only those* directly to the Skia canvas. 
* Because you bypass WPF's layout system and visual tree, painting 60,000 rectangles takes less than a millisecond.

**2. Implement Level of Detail (LOD) / Culling**
If your flame graph is highly detailed, drawing rectangles that are 1 pixel wide is a waste of CPU/GPU cycles.
* **Viewport Culling:** Only iterate through your trace data for the time-window currently visible on the screen. If the user is looking at frame 500, don't process data from frame 10,000.
* **Pixel Culling:** If a function executes so fast that its rectangle width is less than 1 pixel, don't draw it. Draw its parent instead. 

**3. Pre-calculate and Cache the Flame Graph Tree**
Do not parse the execution trace every time the UI repaints. 
* When the trace is loaded, parse it once into a hierarchical tree data structure (Nodes containing Function Name, Start Time, Duration, and Children).
* The UI thread should only read from this pre-built tree.

### Part 3: Architectural Ideas for the Trace/State System

Since you mentioned sluggishness on "fresh app start" and jumping to the end of a long trace, your underlying state-saving mechanism might also be a bottleneck.

**1. Delta Snapshots instead of Full State Dumps**
You mentioned saving "full state, memory, registers, keys, border port" once per frame. Memory is 64KB. If you save 64KB per frame, at 50 FPS, that's 3.2 MB per second. A 5-minute trace is nearly 1 Gigabyte! Loading this on app start will freeze the app.
* **Architecture fix:** Save a *Full Snapshot* only at the start of a frame (or even once every 10 frames). For the subsequent frames, save only the *Deltas* (what memory addresses changed, what registers changed). 
* When jumping to the end of the trace, load the nearest full snapshot, and rapidly apply the deltas in memory. This is exponentially faster to load from disk.

**2. Memory-Mapped Files (mmap)**
If you are currently reading the trace file from disk sequentially using `FileStream`, it will be slow. 
* Use `MemoryMappedFile` in C#. This allows the OS to lazily page the file directly into your application's virtual memory space. You can jump to the end of a 500MB trace file instantly without reading the whole thing into RAM.

**3. Lazy Background Indexing**
When the app starts, you want to show the final screen instantly.
* Load the final frame snapshot immediately and render the screen.
* Spawn a background `Task` to index the trace file (building the flame graph tree, indexing frame boundaries) so the debugger features become available progressively without blocking the UI.

### Summary: How to proceed

1. **Rip out your current Flame Graph UI control.** Replace it with `SkiaSharp` (or `WriteableBitmapEx` if you want to stick to pure WPF without extra libraries).
2. **Decouple the data from the UI.** Build the flame graph tree in a background thread on app startup.
3. **Implement Viewport Culling.** Only issue `DrawRect` calls for functions that fall within the current `ScrollViewer` horizontal/vertical offsets.
4. **Optimize your state loading.** Move to memory-mapped files and delta-compression for your frame states so disk I/O isn't blocking your UI thread on startup.

With this architecture, your app will start instantly, jump to the end of the trace instantly, and scroll/zoom the flame graph at a buttery-smooth 60 FPS, even with millions of function calls represented.
