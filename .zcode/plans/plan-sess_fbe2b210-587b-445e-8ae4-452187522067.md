# "go to $XXXX in code view" — investigate command + unconditional fix

## Difficulty: LOW. Here's why, and here's what actually broke.

**The bug is an index-space mismatch, not missing capability.** The right-click menu builds its trace as `flameTrace` first, window's own tier second (App.fs:7516). Your clicked box's `StartIndex` (282660) lives in the *installed window's* coordinate space, but `flameTrace` was a different, smaller trace (9448 entries — a one-frame bundle installed by an earlier flame click). `goToFlameEntry` then compares indexes from two different traces and refuses. The machinery to *always* honor the command already exists from yesterday's change: `TimelineMaterializer` re-derives any frame (chain-cached; worst case = forward emulation from the first stored state, i.e. "the full trace from the start" — already supported, just linearly slower), and `buildFrameBundle` produces any single frame's exact instruction stream. Determinism (proven by the parity tests) guarantees the bundle's in-frame stream equals the window tier's, so a frame-relative offset maps 1:1.

The only genuinely impossible case: the recording's very first frame (frame 0) — its pre-state doesn't exist in the recording, so no exact mid-frame park is possible for anyone. There we land on the frame boundary and say so, rather than refuse.

## Work plan

### 1. Sister command: "investigate this jump to $XXXX (debug)" — inserted directly below "go to $XXXX in code view"
On click, compute and display a multi-line report:
- **Clicked box**: entry, call site, kind, depth, tick span + duration, and its session frame (midpoint tick → `frameAtTick`).
- **Instruction coordinates**: box's Start/EndIndex in the window tier; frame-relative instruction offset; window `InstrBase` for the frame; absolute instruction range.
- **Index-space health**: installed window (FirstFrame, frames, has entries tier + counts) vs `flameTrace` (entries count, where it came from) — flags MISMATCH when they differ (your exact bug, now visible).
- **Sparse timeline facts**: FrameCount, stored states, `HasState(frame)`, nearest anchor ≤ frame−1, gap frames that materialization must emulate.
- **Code view mode**: execution / memory / graph (`disasmModeMemory`/`disasmModeGraph`).
- **Work plan + verdict**: exactly what the real command will do (tier path or bundle path, steps count, emulation estimate) and today's verdict (CAN JUMP / what would have refused).

Output to both channels:
- `System.Diagnostics.Debug.WriteLine` per line (Debug output window).
- A new mono, wrapped, multi-line `flameDebugLabel` TextBlock with a small header, added to the left `StackPanel` directly below `traceRegenLabel` (the last of the status labels under the registers).

### 2. Fix the real command — `jumpToFlameBox`, one uniform path, no excuses
New function next to `goToFlameEntry`; the "go to $XXXX" item calls it with the clicked window + rect:
1. Resolve the box's frame (midpoint tick), clamped into the recording.
2. Compute the target instruction inside the frame from the **window's own tier** (frame-relative offset of `r.StartIndex`, or first entry whose `Pc = r.Entry` when the tier is absent/trimmed).
3. `buildFrameBundle` on the materializer → exact entries of that frame; target index = same frame-relative offset (determinism) clamped to the bundle; `steps` = real instructions up to it.
4. `ParkAtInstruction(frame, steps)` → `cursor` + `gotoMemCursor(pc)` (both code-window modes) → `refreshAll`/slider/playhead. Status reports what was done, including emulation cost when a gap was materialized.
5. Fallbacks stay honest: frame 0 of a recording → `JumpTo` to the boundary + memory-mode focus, with an explanation; any exception → frame-level seek (existing pattern). Never an "outside the window" refusal again.
6. The "go to exact instruction at tick N" item is rewired through the same function (tick-refined via the bundle's EntryTicks), since it shares the same fragility.

Also removes the stale-`flameTrace`-preference bug itself (window tier wins) so the old `goToFlameEntry` refusal path becomes unreachable from the menu.
